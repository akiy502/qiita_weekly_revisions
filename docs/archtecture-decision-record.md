## ADR-001: 版一覧は revisions ページの埋め込み JSON から取得する

**ステータス:** 承認済み（2026-10-11）

**背景**
Qiita API v2 には編集履歴を返すエンドポイントがない（`GET /api/v2/items/:id/revisions` は 404）。revisions ページ（`/Qiita/items/<id>/revisions?page=N`）の HTML には、`data-component-name="ArticleRevisionsIndexPage"` の `<script>` 要素があり、版の一覧（`createdAt`、`encryptedId`）とページ情報（`isLastPage`）が JSON で入っている。1 ページは 10 件である。

**決定**
revisions ページを `page=1` から順に取得し、埋め込み JSON を解析して版の一覧を得る。

**検討した代替案**
- Qiita API v2：エンドポイントがない。
- ヘッドレスブラウザ（Playwright など）で描画後の DOM を読む：必要なデータは HTML に既に入っており、CI が重くなるだけである。
- 描画済み DOM 要素からの抽出：一覧はクライアント側で描画されるため、取得した HTML には要素がない。

**結果**
- 公開 API ではない内部の構造に依存する。Qiita が画面を作り直すと、予告なく壊れる可能性がある。
- その対策として、読み取れない場合はエラーで止め、既存データを変更しない（spec `revision-collection`）。

## ADR-002: 取得はブラウザではなく Node スクリプトで行う

**ステータス:** 承認済み（2026-10-11）

**背景**
revisions ページの HTML は CORS ヘッダーを返さない。そのため、別オリジンの静的ページから `fetch()` すると拒否される。一方、API v2 は `Access-Control-Allow-Origin: *` を返すが、ADR-001 のとおり使えない。

**決定**
取得は Node スクリプト（`scripts/fetch-revisions.mjs`）で行い、結果をファイルとして commit する。閲覧ページはそのファイルを読むだけにする。取得済みの版は再取得せず、差分だけを追加する。

**検討した代替案**
- 中継用のプロキシやサーバー：運用するものが増える。
- ブックマークレットや UserScript（qiita.com 上で動かす）：CORS の制約は受けないが、「開けば使えるページ」という要件に合わない。

**結果**
- 一度取得した版はファイルに残る。ブラウザのデータを消しても失われず、git で履歴も追える。
- 新しい版を反映するには、スクリプトを実行する必要がある（ADR-008 で自動化する）。

## ADR-003: 版の同一性は数値 snapshot ID で判定する

**ステータス:** 承認済み（2026-10-11）

**背景**
`encryptedId` は `<base64("\"ArticleSnapshot-<数値>\"")>--<署名>` という形である。前半からは版の数値 ID を取り出せる。後半は署名で、自分では作れず、Qiita 側の鍵の変更で値が変わり得る。

**決定**
差分取得、重複の排除、既読管理のキーには、前半を base64 デコードして得た数値 snapshot ID を使う。遷移用の URL には、取得した最新の `encryptedId` をそのまま使う。

**検討した代替案**
- `encryptedId` 全体をキーにする：署名が変わると、同じ版が別の版として扱われる。既読が消え、データも重複する。

**結果**
- `encryptedId` の形式が変わってデコードできなくなった場合は、ADR-001 と同様に取得を中断する。

## ADR-004: データは `revisions.js` として `<script>` 要素で読み込む

**ステータス:** 承認済み（2026-10-11）

**背景**
閲覧ページは GitHub Pages で公開するが、開発中はローカルの `file://` でも開けるようにしたい。`file://` では `fetch()` で JSON ファイルを読めない。

**決定**
データファイルは `site/revisions.js`（`window.REVISIONS = [...];`）にして、`<script src="revisions.js">` で読み込む。整形の方法は固定し、差分がなければバイト単位で同一になるようにする。

**検討した代替案**
- `revisions.json` を `fetch()` で読む：`file://` では動かない。
- データを `index.html` に直接埋め込む：取得のたびに HTML 全体が書き換わり、差分が読みにくくなる。

**結果**
- 取得スクリプトは、JS の外枠を取り除いてから JSON として解析する必要がある。

## ADR-005: 閲覧ページはフレームワークなしの単一 HTML にする

**ステータス:** 承認済み（2026-10-11）

**背景**
画面は、更新日の一覧、未読のみフィルタ、既読管理、エクスポートとインポートだけである。

**決定**
`site/index.html` 1 枚に、素の HTML、CSS、JS で書く。ビルド工程も実行時の依存も持たない。JST への変換には `Intl.DateTimeFormat` を使う。lint と整形には Ultracite を開発時だけ使う。

**検討した代替案**
- React や Vite など：ビルドと依存の更新が必要になるのに、この規模では得られるものがない。

**結果**
- 機能が大きく増えた場合は、この決定を見直す。

## ADR-006: 既読は localStorage に保存し、端末間はエクスポート／インポートで移す

**ステータス:** 承認済み（2026-10-11）

**背景**
閲覧者は PC と iPhone の両方で見る。端末間で既読を自動同期するにはバックエンド（認証と保存先）が必要で、構成が一段大きくなる。

**決定**
- 既読は閲覧者のブラウザの localStorage に、キーのプレフィックス `qiita-weekly-revisions:` を付けて保存する。
- 端末間の自動同期は行わない。代わりに、JSON のエクスポートとインポートを用意する。方法はファイルとテキスト（コピーと貼り付け）の両方に対応する。
- インポートは既定でマージ（和集合）とし、上書きは確認ダイアログの後に行う。

**検討した代替案**
- バックエンド（Azure Functions と Table Storage など）による同期：今回は必要ないと判断した。
- 既読をリポジトリのファイルに書く：閲覧者ごとの状態を、公開リポジトリに置くことになる。

**結果**
- iOS Safari では、7 日間開かなかったサイトの localStorage が消える（ITP）。ホーム画面に追加すると対象外になることを、画面に注記する。
- ストレージが使えない環境でも、一覧の表示と遷移は動作させる。

## ADR-007: GitHub Pages で公開する

**ステータス:** 承認済み（2026-10-11）

**背景**
当初はローカルの `file://` で開ければ十分と考えていた。しかし iPhone では、ローカルの HTML は「ファイル」App の Quick Look で開かれ、JS が動かない。そのため、iPhone でも見るには静的ホスティングが必要になる。

**決定**
public リポジトリ `qiita_weekly_revisions`（既定ブランチは `main`）の GitHub Pages で、`site/` を公開する。

**検討した代替案**
- Azure Static Web Apps：無料で使えるが、GitHub Actions との組み合わせでは GitHub Pages のほうが手間が少ない。
- ローカルの `file://` のみ：iPhone で使えない。

**結果**
- 無料で使うためにリポジトリは public になる。公開してよいファイルだけを追跡しているか、push 前に確認する。

## ADR-008: 取得から公開までを 1 本のワークフローで行う

**ステータス:** 承認済み（2026-10-11）

**背景**
版は JST の木曜と日曜の 05:12 ごろに作られる。`GITHUB_TOKEN` で push した commit は、別のワークフローの `on: push` を発火させない。そのため、「取得して commit するワークフロー」と「push で公開するワークフロー」に分けると、自動取得した結果が公開されない。

**決定**
`.github/workflows/update.yml` の 1 本で、次の処理を行う。
- `schedule`（cron `0 21 * * 3,6`、JST の木・日 06:00）と `workflow_dispatch`：取得し、差分があれば commit して、同じ実行の中で公開する。
- `push`（`main`）：取得せずに公開だけ行う。

**検討した代替案**
- ワークフローを 2 本に分け、PAT で push して連鎖させる：PAT の管理が増える。
- `workflow_run` で連鎖させる：動きが追いにくくなるのに、得られるものは 1 本にまとめる場合と変わらない。

**結果**
- bot の commit が再びワークフローを起動することはなく、無限ループは起きない。
- GitHub の schedule は遅れたりとばされたりすることがあるが、版は消えないので、次の実行か手動実行で取り戻せる。
- public リポジトリでは、60 日間活動がないと schedule が無効になる。版は週 2 回増えて commit されるので、通常は該当しない。

## ADR-009: リポジトリの初期設定は `gh` CLI スクリプトで行う

**ステータス:** 承認済み（2026-10-11）

**背景**
GitHub リポジトリの作成、初回 push、Pages の有効化を、手作業ではなくコードとして残したい。対象は個人用の 1 リポジトリである。

**決定**
`scripts/bootstrap.sh` に `gh` CLI で手順を書く。どの段階も「既にあれば何もしない」ようにして、再実行しても安全にする。内容はブランチの `main` への改名、リポジトリの作成と push、Pages の有効化（`build_type=workflow`）である。認証は実行者の `gh auth login` に任せ、秘密情報はコードに含めない。

**検討した代替案**
- Terraform（`integrations/github` provider）：あるべき状態を宣言して管理できるが、1 リポジトリでは state ファイルと PAT の管理の手間が見合わない。

**結果**
- 実行には `gh` のインストールとログインが前提になる（利用者が手動で行う）。
- 設定のずれを自動で検出する仕組みはない。設定を変えたらスクリプトも更新する。
